# Evaluation

> **Every metric on this page is measured on synthetic data.** Kosh has no real
> payment history yet. The data comes from our own generator, whose churn
> process we wrote, so a model can learn exactly the relationships we put in.
> These numbers show that the method works end to end and that it is evaluated
> honestly. They do not predict how it would do on real merchants.

What is evaluated here:

1. [The churn model](#1-churn-model) against the rule score it replaces (details of the model: [model card](model-card.md)).
2. [Fairness](#2-fairness): whether churn and agent-pattern flags skew by district, category or size.
3. [The AI guard](#3-ai-guard-and-prompt-injection): replies rejected, and a prompt-injection test set.
4. [Admin reviews](#4-admin-reviews-of-flags): how confirm / dismiss decisions become labels.

Reproduce everything: `npm run ml` (≈ 2 minutes; see [How to reproduce](#how-to-reproduce)).

## 1. Churn model

**Data.** `scripts/generate-large.mjs` simulates 1,600 merchants, 80 agents and 4,000 customers in 8 districts over 330 days (≈ 710,000 transactions). It writes to `data/` (gitignored) and never to a database. Each merchant has a daily hazard of deciding to leave, raised by short tenure, small size, customers concentrated in a few people, few repeat customers, failed payments, refunds, a category effect and an unobserved random "frailty". Of those who decide, 65% fade out over 10–45 days and 35% stop at once; 8% come back later. Merchants who stay sometimes have a 7–20 day dip that looks like a decline. **District has no effect.** 437 of 1,600 merchants decide to leave at least once.

**Label.** A verified merchant with no successful payment in the 30 days after a snapshot date.

**Features.** Computed by the app's own code (`src/services/mock/intelligence/churn-features.ts`) strictly from before the snapshot, so training and scoring can't drift apart. The rule score's five factors (days since last payment, payment-count drop, value drop, failure rate, refund rate) plus tenure, 8-week trend, top-customer share, repeat-customer share, payment volume and active days. One row per merchant per weekly snapshot, for merchants with enough history for the model (tenure ≥ 30 days, ≥ 5 payments in 60 days): 36,681 rows from 30 snapshots, 5.0% positive.

**Split.** By merchant *and* by time. A hash of the merchant id sends 30% of merchants to test. Test uses the last 8 weekly snapshots; train uses only snapshots whose 30-day label window ends before the first test snapshot. No merchant and no label window is on both sides (the script asserts both). The model is chosen inside train (earlier snapshots of 80% of train merchants → later snapshots of the other 20%), never on test. Confidence intervals resample whole merchants, since each merchant appears in several snapshots.

**Models.** Logistic regression (standardised features) and gradient boosting (200 trees of depth 3), both scikit-learn with a fixed seed. Logistic regression is kept unless boosting beats it on validation PR-AUC by 0.01 or more.

**Reading these results.**

- **The full test set flatters every method.** It includes merchants who had already gone quiet before the snapshot; "no payment for 3 weeks → won't pay next month" is easy. The second table keeps only merchants paid in the 14 days before the snapshot: the cases where a warning is still useful.
- **On those hard cases the model ranks better than the rule score, but the evidence is thin.** There are only a few dozen churners in that subset, and the confidence intervals overlap. We can't claim the gap is real at this sample size.
- **Calibration.** The model's probabilities track observed churn (ECE under 0.01), so the admin page shows the score as a percentage: "chance of no payment in the next 30 days". The rule score is not a probability.
- **Flags.** On the levels the admin page uses (HIGH ≥ 50%, MEDIUM ≥ 15%), model HIGH beats rule HIGH on both precision and recall. At HIGH-or-MEDIUM the model is far more precise than the rule but catches slightly fewer churners (see "Flags shown on the admin page").
- **What it relies on.** Mostly recency and activity. The tenure, concentration and repeat-share effects the generator builds in are weak next to the decline itself, so the model barely uses them.

## 2. Fairness

`scripts/fairness.mjs` scores the test merchants and snapshots exactly as the admin page does, and runs the agent-pattern rules on every agent at three dates. Because the generator gives district no effect and plants agent patterns at random, a fair method should show no district skew. Category and size *do* change churn risk by design, so differences in how often a group is flagged are expected there. What matters is whether the **error rates** differ: recall (churners caught) and false-positive rate (merchants who stayed but were flagged).

**Reading these results.**

- **District: no measurable skew.** The intervals for false-positive rate and recall overlap across districts.
- **Size: small merchants who stay are flagged more often.** Their false-positive rate is a few percent against near zero for large merchants, and the intervals do not overlap. This is the expected cost of judging a quiet shop on few payments; the old rule score has the same skew, much larger. Small merchants are also the ones who churn most. Mitigation on the page: flags are prompts to call, not decisions, and an admin can dismiss them (section 4).
- **Category:** there is a false-positive gap between categories. It may follow size (service and "other" merchants are smaller on average), but retail, also low-volume, has a low rate. We have not separated the two effects.
- **Agent patterns:** every planted pattern was caught, and false flags were rare. But with 10 planted agents, the per-group counts are far too small to show or rule out a skew. The planted patterns are also stronger than real misconduct would be.

## 3. AI guard and prompt injection

The model only words figures the code computed; a reply is used only if it passes the guard (`src/server/ai/guard.ts`): JSON of the right shape, the requested language, every number present in the facts, no markup or links, and no mention of PINs, passwords, OTPs or codes. Otherwise the next model or the deterministic template answers.

**Prompt-injection test set** (`scripts/lib/prompt-injection.json`, checked by `tests/ai-guard.test.ts` and `node scripts/check-ai.mjs`):

| | Count | Result |
|---|---|---|
| Hijacked replies (invented amounts and phone numbers, links, script tags, markdown, PIN/OTP requests in English and Bengali, extra JSON fields, non-JSON) | 14 | all rejected, each for the expected reason |
| Known limitations: an echoed instruction, a misleading claim with no figures, a money suggestion with no amount | 3 | accepted: the guard checks form, not meaning |
| Benign controls (English, Bengali digits) | 2 | accepted |
| Hostile payloads planted in a district name, each answered by a stub model that obeys | 7 | all dropped; the template answered |

Two fixes came out of building this set:

1. **Credential requests passed the guard.** "Please share your PIN with support" has no numbers or links. The guard now rejects any mention of PINs, passwords, OTPs, one-time codes or CVVs.
2. **Planted text could bring its own numbers.** The guard accepts any number found in the facts, so a district name carrying "send ৳50,000 to 01712345678" would have made those figures "allowed". Place names are now reduced to letters, spaces and basic punctuation before they reach a model (`placeName` in `src/server/ai/kinds.ts`).

Today no free text typed by users reaches a model: districts are set in the database, and categories come from a fixed list. The test set guards against planted data and future fields.

**Guard statistics on real model replies: not measured yet.** `node --env-file=.env.local scripts/check-ai.mjs --live` asks the configured models for every insight in English and Bengali, plus the injection payloads, and reports the share of replies rejected and why, per model. It writes `ml/reports/guard-stats.md`. It wasn't run for this page because it spends API quota on your keys. Run it and paste the table here.

## 4. Admin reviews of flags

On the Intelligence page, every agent-pattern flag and every MEDIUM/HIGH churn flag has **Confirm** and **Dismiss**. Each decision is stored in `flag_reviews` with the flag's value and severity at that moment, plus the reviewer and time, and written to the audit log (`FLAG_CONFIRMED` / `FLAG_DISMISSED`). Decisions are never edited: a new decision supersedes the old on the page and the history stays. Run `supabase/migrations/20261008_flag_reviews.sql` first; until then the page shows the flags but refuses to save a decision.

These decisions are the first real labels Kosh will have. Once there are enough, the precision of agent-pattern flags and of churn flags can be measured on real data. **There are none yet, so no such number is reported.**

## How to reproduce

```bash
npm run ml          # dataset → features → train → export → fairness (fixed seeds)
npm test            # includes tests/churn-model.test.ts: the TypeScript scorer against Python's predictions
```

Needs Node 22.18+ and Python 3.11+ (`ml/requirements.txt` pins the packages; a virtualenv is created in `ml/.venv`). Full reports: `ml/reports/metrics.md`, `ml/reports/fairness.md`.
